# 手机记录表单渐进增强设计规格

## 1. 目标

缩短手机端日常记录表单的视觉长度，补齐力量训练多动作的界面操作，并确保动态字段仍具备服务端校验、用户隔离和草稿恢复能力。

本功能不改变数据库结构、记录字段或既有保存路由。

## 2. 采用方案

采用渐进式记录表单：

- 饮食的营养字段按需展开；
- 运动的力量动作按需展开；
- 力量动作可动态新增和删除；
- 手机端保存操作保持易触达；
- 数字输入调用更合适的软键盘；
- JavaScript 只增强体验，服务端仍是数据正确性和权限的最终依据。

不采用只增加固定保存按钮或只调整间距的方案，因为它们无法解决普通新建页只能输入一条力量动作的核心缺口。

## 3. 饮食表单

基础字段始终显示：记录时间、餐次、食物、份量/备注、饱腹感。

热量、蛋白质、碳水化合物和脂肪放入标题为“可选营养信息”的原生 `<details>` 区域。以下任一条件成立时自动展开：

- 服务端初始数据中任一营养字段有值，例如复用历史记录；
- POST 校验失败后任一营养字段仍有提交值；
- 任一营养字段存在校验错误；
- 本地草稿恢复后任一营养字段有值。

用户手动展开或折叠不改变字段值。所有营养字段仍为可选，全部留空时可正常保存。

## 4. 运动与力量明细

运动通用字段始终显示：记录时间、运动类型、时长、强度和备注。

力量动作放入标题为“力量训练明细”的原生 `<details>` 区域：

- 当前运动类型为“力量训练”时自动展开；
- 复用记录包含力量动作时自动展开；
- 校验失败或本地草稿含力量动作时自动展开；
- 其他运动类型默认折叠；
- 用户从“力量训练”切换为其他类型时只折叠，不清空或删除已经填写的动作。

每个动作行显示动作名称、组数、每组次数和可选负重，以及一个“删除本条”按钮。页面底部提供“添加动作”按钮。

新增动作：

- 使用 Django inline formset 的 `empty_form` 作为模板；
- 新行索引使用当前 `TOTAL_FORMS`，然后递增 `TOTAL_FORMS`；
- `order` 隐藏字段设置为新行索引；
- 新行不包含任何服务端对象 ID；
- 新增后焦点移动到动作名称输入框。

删除动作：

- 勾选该行的 `DELETE` 字段并隐藏整行；
- 不重排已有表单索引或对象 ID；
- 已删除行不计入界面上的有效动作数量；
- 至少保留一个可见空行，便于继续输入；
- 删除后更新各行顺序字段和按钮状态。

最多允许 20 条未删除动作。达到上限时禁用“添加动作”按钮并显示“最多添加 20 条”。客户端限制只用于即时反馈，现有服务端 `max_num`、自定义最终数量校验、owner-scoped 子记录校验和父记录行锁保持不变。

## 5. 草稿恢复协议

当前草稿脚本只在首次加载时收集字段，无法保存动态新增行。本功能将草稿格式扩展为：

- 普通字段仍按字段名保存；
- 新增 `__formset_totals` 元数据，记录每个动态 formset 保存草稿时的 `TOTAL_FORMS`；
- 不把 Django 管理字段当作普通字段直接恢复；
- 密码、文件、CSRF、提交按钮和服务端对象 ID 不写入草稿。

恢复顺序：

1. 读取并解析草稿；
2. 请求 formset UI 将渲染行数补足到草稿记录数量；
3. 重新扫描当前 DOM 中的安全字段；
4. 按字段名恢复值；
5. 根据恢复后的字段值更新折叠区和删除状态。

恢复只能增加行数，不能减少服务端已经渲染的行数。例如服务端复用记录渲染 3 条动作，而旧草稿只记录 1 条时，必须保留 3 条；草稿有 3 条而普通新建页只有 1 条时，补足到 3 条。

旧版草稿没有 `__formset_totals` 时继续恢复现有字段，不报错。无效 JSON 继续清除。

## 6. 页面结构与脚本边界

`templates/tracker/record_form.html` 根据表单类型显式渲染分区，不再对所有记录表单完全依赖 `form.as_p`：

- 饮食表单渲染基础区和营养 `<details>`；
- 运动表单渲染通用区、formset 管理字段、动作行和 `empty_form` 模板；
- 身体指标表单保持简单字段列表；
- 所有字段错误、非字段错误、帮助文本和隐藏字段必须保留。

视图向模板传入稳定的 `form_kind`（`meal`、`exercise`、`measurement`），避免模板根据标题文字猜测类型。

新增 `static/js/record-form.js`，职责仅包括：

- 动态 formset 行增删；
- 有效动作计数和 20 条限制；
- 运动类型与力量折叠区联动；
- 草稿脚本调用的“补足行数”接口；
- 字段恢复后的界面同步。

`static/js/draft-form.js` 继续负责草稿存取和成功保存后的清理，不复制 formset DOM 操作逻辑。两个脚本通过自定义 DOM 事件和一个最小的 `window.healthRecordForms` 接口协作。

## 7. 手机输入与操作区

- 整数输入使用 `inputmode="numeric"`；
- 小数输入使用 `inputmode="decimal"`；
- 手机端保存按钮容器使用 `position: sticky`，位于视口底部导航上方；
- 保存区使用不透明背景和顶部边框，滚动时不遮挡字段错误；
- 新增、删除和保存按钮触控高度至少 44 像素；
- 360、390、430 和 1280 像素宽度不得产生页面级横向滚动。

## 8. 无 JavaScript与异常处理

- 无 JavaScript 时，服务端现有表单和所有已渲染 formset 行仍可提交；
- JavaScript 不生成或信任用户 ID、父记录 ID或子记录 ID；
- 动态行模板缺失时，隐藏“添加动作”按钮，不影响基础运动保存；
- 草稿存储不可用或配额失败时，不阻止表单输入和提交；
- 服务端校验失败后保留所有字段与错误，并自动展开包含错误的分区；
- 提交期间沿用现有草稿令牌机制，不引入网络请求或后台同步。

## 9. 测试策略

### 9.1 表单与模板测试

- 饮食基础字段和营养字段分区正确；
- 复用营养记录或营养错误时折叠区展开；
- 运动视图提供 `form_kind`、管理字段和无 ID 的 `empty_form`；
- 数字字段具有正确 `inputmode`；
- 所有错误和隐藏字段仍可渲染。

### 9.2 浏览器测试

- 选择力量训练会展开明细；
- 可新增多条动作、删除其中一条并成功保存剩余动作；
- 新增后焦点进入动作名称；
- 有效动作达到 20 条时禁止继续新增；
- 动态三行草稿刷新后完整恢复；
- 服务端复用三行时不被旧的一行草稿截断；
- 营养草稿恢复后自动展开；
- 360、390、430 和 1280 像素下无溢出且操作按钮达到 44 像素。

### 9.3 回归与安全测试

- 现有跨账号/跨父子记录 UUID 篡改测试继续通过；
- 现有 20 条最终数量和并发父锁测试继续通过；
- 无 JavaScript 的服务端多行 POST 继续通过；
- 饮食、运动和身体指标的创建、编辑、复用及草稿清理流程继续通过。

## 10. 不在本次范围

- 拖拽排序力量动作；
- 动作名称自动补全或动作数据库；
- 训练模板收藏；
- 离线提交队列；
- PWA 安装；
- 图片上传；
- 修改数据库模型。
